이 문서는 지금까지 정해진 프로젝트 방향을 하나의 기준으로 통합한다. 게임 콘셉트, 플레이 구조, 세계관 선택, 플레이어 신체 표현, 환경·물리·음향·시각 시스템, 브라우저 기술 구조, 품질 검증, 개발 순서를 정의한다.

## 1. 제품 비전

### 1.1 핵심 비전

브라우저 안에서 실행되지만, 단순한 웹 슈팅 게임이 아닌 **과학적 근거를 가진 현실주의 1인칭 전장 시뮬레이션**을 지향한다. 플레이어는 전장의 바깥에서 부대를 지휘하는 것이 아니라, 1인칭 시점으로 게임 세계 안에 존재한다.

그래픽만 현실적으로 보이게 만드는 것으로는 목표를 달성할 수 없다. 물체의 움직임, 재질과 접촉, 바람과 날씨, 소리의 공간감, 플레이어의 신체 표현, 시각 입력이 서로 일관된 규칙을 공유해야 한다.

### 1.2 설계 원칙

1. **Reality-based, not reality-themed:** 현실처럼 보이는 연출보다 현실의 원리를 바탕으로 한 동작을 우선한다.
2. **Evidence before claims:** 과학적 사실을 주장할 때 근거와 적용 범위를 기록한다.
3. **No fake completion:** 구현되지 않은 기능을 완료된 기능처럼 표시하지 않는다.
4. **One world, shared rules:** 동일한 세계 안에서 물리·재질·환경·음향 규칙이 일관되게 적용되어야 한다.
5. **Render and simulation are separate:** 그래픽 품질을 낮춰도 게임 상태와 핵심 시뮬레이션 규칙은 임의로 바뀌지 않아야 한다.
6. **Web is a hard requirement:** 데스크톱 앱이나 네이티브 게임으로 전환하지 않는다. 브라우저 실행을 제품의 핵심 조건으로 유지한다.
7. **Measured approximation:** 현실을 그대로 계산할 수 없는 영역은 근사 모델과 한계를 공개한다.

### 1.3 비목표

- 국가 운영이나 세계 지도를 중심으로 한 대전략 게임이 아니다.
- RTS 부대 지휘 게임이 아니다.
- 온라인 멀티플레이 게임이 아니다.
- 특정 기존 게임의 스토리, 맵, 캐릭터, UI를 복제하지 않는다.
- “현실 100% 복제”를 기술적으로 보장한다고 주장하지 않는다.
- 현실 무기 사용, 폭발물 작동, 공격용 무인기 운용을 학습할 수 있는 실용적 시뮬레이터를 만들지 않는다.

## 3. 게임 구조와 플레이 흐름

### 3.1 시작 흐름

1. 게임 로딩 및 장치 호환성 검사
2. 그래픽·오디오 초기 설정
3. 세계관 선택 화면 표시
4. REAL WORLD 또는 FICTIONAL WORLD 선택
5. 해당 세계관의 저장 데이터와 콘텐츠 목록 로드
6. 플레이 콘텐츠 진입

### 3.2 세계관 선택

| 모드 | 정의 | 콘텐츠 원칙 |
|---|---|---|
| REAL WORLD | 실제 국가와 현실 지리·건축을 기반으로 하는 세계 | 시나리오는 창작한다. 실제 국가의 존재와 지리적 특징을 존중하되 현실의 진행 중인 분쟁을 전술 안내처럼 재현하지 않는다. |
| FICTIONAL WORLD | 국가·지리·역사·정치 구조를 새로 만든 세계 | 자체 지도, 국가, 도시, 문화, 역사 및 분쟁 배경을 일관된 설정 문서로 관리한다. |

두 모드는 메뉴 이름만 다른 동일한 맵이어서는 안 된다. 세계관 데이터, 위치 정보, 도시 자산, 인물, 임무 설정을 독립 패키지로 관리한다.

### 3.3 플레이 루프

현재 확정된 것은 싱글플레이 1인칭 전장 참여라는 점이다. 미션 구조는 아직 미정이다. 우선 아래의 중립적인 플레이 루프를 기준으로 프로토타입을 만든다.

- 게임 세계 진입
- 주변 환경과 상황을 관찰
- 이동 및 상호작용
- 목표 또는 사건을 수행
- 환경 변화와 NPC 반응 확인
- 임무 또는 시나리오 결과 저장

구체적인 공격 절차, 실제 무기 운용, 폭발물 사용법을 재현하는 콘텐츠는 설계 범위에서 제외한다. 전투의 묘사는 게임 전용 규칙과 서사적 연출로 구성한다.

## 4. 플레이어 신체 및 1인칭 시점

### 4.1 Full-body First Person

카메라만 공중에 떠 있는 구조를 사용하지 않는다. 플레이어는 머리, 몸통, 팔, 다리, 발, 의복, 휴대 장비를 포함한 전신 모델을 가진다.

| 구성 | 요구사항 |
|---|---|
| Head / View | 카메라가 머리 위치와 방향에 연결됨 |
| Torso | 아래를 볼 때 상체가 자연스럽게 보임 |
| Arms | 시점과 동작에 맞춰 연결된 형태로 표시 |
| Legs / Feet | 고개를 숙이거나 자세를 바꿀 때 다리와 발이 보임 |
| Clothing | 움직임에 따른 주름·흔들림을 표현 |
| Equipment | 착용 위치와 캐릭터 움직임이 일치 |
| Shadow | 몸과 장비의 위치에 맞춰 그림자를 생성 |

전신 모델과 1인칭 카메라가 서로 다른 애니메이션을 재생해 위치가 어긋나는 현상을 방지해야 한다. 1인칭 렌더링 전용 메시를 쓰더라도 몸의 기준 좌표와 애니메이션 상태는 공유한다.

### 4.2 독립적인 좌우 눈 시스템

좌우 눈꺼풀을 별도의 입력 상태로 관리한다. 사용자는 한쪽 눈 또는 양쪽 눈을 각각 감을 수 있어야 한다.

| 왼쪽 눈 | 오른쪽 눈 | 시각 상태 |
|---|---|---|
| 열림 | 열림 | 양안 시야 |
| 닫힘 | 열림 | 오른쪽 눈 중심의 단안 시야 |
| 열림 | 닫힘 | 왼쪽 눈 중심의 단안 시야 |
| 닫힘 | 닫힘 | 외부 시각 입력 차단 |

입력은 누르고 있는 동안 닫힘 상태를 유지하고, 놓으면 열리는 Hold 방식으로 설계한다. 좌우 키 배치는 사용자가 설정에서 변경할 수 있어야 한다.

### 4.3 깜빡임과 눈물막 표현

눈꺼풀 움직임, 눈물막 상태, 시각 입력, 시각 적응을 하나의 변수로 합치지 않는다.

- Eyelid State: 좌우 눈꺼풀의 열림·닫힘 상태
- Blink Event: 자연스럽고 짧은 깜빡임 이벤트
- Tear-film State: 눈 표면의 수분막을 표현하는 게임 내부 상태
- Ocular Comfort: 건조감 등 불편감의 추상적 표현
- Visual Adaptation: 밝기 변화 이후 시각이 적응하는 과정
- Visual Input: 좌우 눈에서 들어오는 화면 정보

실제 생리학을 참고하되 의학적으로 검증된 치료·손상 모델이라고 주장하지 않는다. 눈을 감는 것만으로 눈의 건조나 시각 피로가 즉시 해결되는 것처럼 표현하지 않는다. 눈물막과 시각 적응은 서로 다른 현상으로 다룬다.

### 4.4 접근성

눈 감기 입력은 기본 키 변경이 가능해야 한다. 시각 교란, 이명, 흔들림, 카메라 움직임을 각각 조절할 수 있어야 한다. 민감한 사용자를 위해 강한 화면 깜빡임을 줄이거나 정적 대체 효과를 선택할 수 있어야 한다.

## 5. 그래픽과 월드 표현

### 5.1 시각 목표

목표는 포토리얼리즘이다. 카툰, 로우폴리, 의도적인 스타일라이즈드 아트는 기본 방향이 아니다. 다만 브라우저와 GPU의 한계 때문에 모든 기기에서 동일한 시각 품질을 보장하지 않는다.

### 5.2 그래픽 요구사항

| 항목 | 목표 |
|---|---|
| Geometry | 실제 건축·지형·물체의 비례와 실루엣을 반영 |
| Materials | PBR 기반 표면 표현 |
| Textures | 표면의 미세한 차이와 실제 재질감을 표현 |
| Lighting | 시간대·광원·환경광 변화 표현 |
| Shadows | 접촉 그림자와 거리별 그림자 품질 관리 |
| Atmosphere | 안개·먼지·습도·대기 원근 표현 |
| Weather | 강수·구름·바람 등 환경 상태 연동 |
| Vegetation | 식생의 형태와 환경 반응 표현 |
| Water | 반사·굴절·파동은 성능에 맞춰 단계화 |
| Animation | 전신·의복·환경 요소의 움직임을 일관되게 표현 |

### 5.3 렌더링 원칙

- 렌더러는 시뮬레이션 상태를 읽어 화면을 만든다. 렌더링 결과가 물리 상태의 원본 데이터가 되어서는 안 된다.
- 고품질 효과를 지원하지 않는 환경에서는 대체 렌더링 경로를 사용한다.
- 동일한 장면에서 렌더링 품질 설정을 바꿔도 충돌·상태·저장 데이터가 달라지지 않아야 한다.
- 임의의 화면 후처리로 현실감을 과장하기보다 재질, 조명, 지오메트리, 애니메이션의 기본 품질을 먼저 확보한다.

## 6. 환경 및 일반 물리 시뮬레이션

### 6.1 물리 시스템의 범위

중력, 충돌, 회전, 마찰, 미끄러짐, 물체의 운동 상태 등 **일반적인 월드 물체의 물리적 상호작용**을 우선한다. 물리 계산은 고정 시간 간격 또는 검증된 시간 관리 방식을 사용하고, 프레임 렌더링 주기와 분리한다.

### 6.2 표면과 재질

표면은 단순한 텍스처 이름이 아니라 물리적 상호작용을 정의하는 재질 프로필을 가진다.

| 표면 유형 | 게임 내 표현 목표 |
|---|---|
| 얼음 | 미끄러짐이 쉽게 발생하고 감속 특성이 다름 |
| 콘크리트 | 거칠고 단단한 접촉 특성 |
| 아스팔트 | 표면 상태에 따른 접촉 및 감속 차이 |
| 흙·진흙 | 표면 변형과 이동 저항을 추상적으로 표현 |
| 모래 | 입자성 표면의 흔적과 침하를 제한적으로 표현 |
| 잔디 | 지표면과 식생이 함께 반응 |
| 금속 | 표면 마감 상태에 따른 접촉 특성 |

재질 프로필은 일반 물체 상호작용에 일관되게 적용한다. 물체는 바닥에 닿자마자 무조건 정지하는 대신, 게임 내부 물리 상태에 따라 미끄러짐·구름·회전·감속을 표현한다. 구체적인 물성 수치는 각 맵의 게임 밸런스와 성능 검증을 거쳐 정한다.

### 6.3 바람과 환경장

바람은 장면 전체에 동일한 숫자를 넣는 장식 효과가 아니라, 위치와 시간에 따라 달라질 수 있는 환경 데이터로 설계한다.

- 바람 방향과 세기의 시간 변화
- 돌풍과 불규칙한 변화의 시각적 표현
- 지형과 건축물 주변의 바람 차이를 표현하는 게임용 근사장
- 식생, 먼지, 연기, 의복 등 환경 요소의 반응
- 기상 상태와 바람 상태의 연결

이 시스템은 환경의 움직임과 분위기를 위한 게임 시뮬레이션이다. 실제 무기 발사 보정이나 현실 탄도 계산에 사용할 수 있는 데이터·절차를 제공하지 않는다.

### 6.4 발사체 관련 범위

조준점과 게임 내 충돌 결과를 분리하는 것이 디자인 목표다. 다만 발사체 움직임은 실제 무기별 성능표, 실측 탄도, 거리별 보정값, 실전 사격 계산을 복제하지 않는 **게임 전용 추상 모델**로 제한한다. 과학적 원리의 일관성은 유지하되 현실 무기 운용에 전용할 수 있는 정확한 수치 체계는 제공하지 않는다.

## 7. 감각·시야 효과

### 7.1 시각 상태와 화면 효과 분리

화면 전체에 흰색 필터를 씌우는 것만으로 감각 효과를 구현하지 않는다. 월드 렌더링, 좌우 눈 입력, 시각 적응, 캐릭터의 인지 상태를 별도 모듈로 관리한다.

### 7.2 강도 변화

섬광 및 감각 교란은 반복 재생되는 동일한 프리셋만 사용하지 않고, 시나리오가 허용한 게임 전용 범위 안에서 변화할 수 있다. 변화는 연출 다양성을 위한 것이며 실제 폭발 강도, 인체 손상 임계값, 의학적 피해 수치를 모델링하지 않는다.

| 내부 상태 | 게임 표현 예시 |
|---|---|
| Visual Disturbance | 밝기 적응 및 일시적인 시야 교란 |
| Afterimage | 잔상 표현 |
| Contrast Reduction | 대비 인식 저하를 표현하는 화면 상태 |
| Audio Disturbance | 소리의 선명도·방향감 변화 |
| Recovery | 시각·청각 효과를 별도로 완화 |

시각과 청각의 효과는 서로 독립적으로 회복한다. 눈을 감는 입력이 청각 상태를 자동으로 바꾸지는 않는다. 모든 효과에는 강도 조절과 접근성 대체 옵션을 제공한다.

## 8. 장비 및 콘텐츠 시스템

### 8.1 데이터 기반 장비 등록

장비는 소스 코드 안에 개별적으로 하드코딩하지 않고 데이터 등록 구조로 관리한다. 이 문서에서 장비 모듈은 게임 내 가상 콘텐츠의 자산·상태·애니메이션·UI 일관성을 관리하는 목적이다. 현실 장비의 작동법, 조작 순서, 성능표, 공격 절차를 재현하는 목적이 아니다.

### 8.2 장비 공통 스키마

| 필드 | 설명 |
|---|---|
| id | 변경되지 않는 내부 식별자 |
| displayName | 게임 내 표시 이름 |
| category | 콘텐츠 분류 |
| assetReference | 3D 모델·텍스처 묶음 참조 |
| audioReference | 관련 오디오 자산 참조 |
| animationSet | 게임 연출용 애니메이션 묶음 |
| stateModel | 게임 전용 상태 전이 정의 |
| interactionUI | 사용자 인터페이스 설정 |
| qualityTier | 에셋 품질 및 LOD 정책 |
| licenseMetadata | 출처·라이선스·사용 범위 |
| validationProfile | 필수 기능 검사 목록 |

### 8.3 누락 방지 규칙

새 장비를 추가할 때 필수 자산과 상호작용 검사를 통과하지 않으면 완료 상태로 표시하지 않는다.

- 모델 파일과 텍스처 참조 확인
- 애니메이션 세트 연결 확인
- 오디오 자산 참조 확인
- 게임 상태 전이의 유효성 검사
- UI 표시와 상태 값 일치 검사
- 장비 전환 및 저장·불러오기 검사
- 이전 장비에 대한 회귀 테스트

장전 등 장비별 상태는 게임 내부의 추상 상태로 관리할 수 있다. 실제 장비의 단계별 조작 절차나 실물 사용법을 재현하지 않는다.

### 8.4 원거리 장비 및 조준 화면

플레이어가 보는 조준 표시와 게임 세계의 상호작용 결과는 같은 값으로 취급하지 않는다. 조준 화면은 시각 인터페이스이고, 게임 세계의 결과 판정은 게임 전용 시뮬레이션 계층이 담당한다. 현실 무기별 조준·탄도 계산, 실측 보정 데이터, 실제 사격 성능표는 범위에서 제외한다.

### 8.5 무인 장비와 컨트롤러

무인 장비와 전용 컨트롤러는 게임 콘텐츠의 일부로 표현할 수 있다. 단, 실제 원격조종 절차, 주파수·통신 링크, 폭발물 탑재·작동, 공격 비행 경로 등의 현실 운용 기능은 구현하지 않는다. 컨트롤러는 게임 전용 UI와 상태 표시를 제공하는 가상 인터페이스로 제한한다.

## 9. 오디오 시스템

### 9.1 실제 녹음 기반 자산

사운드는 가능한 범위에서 직접 제작한 녹음 또는 사용 권한이 명확한 라이선스 자료를 기반으로 구성한다. 출처가 불분명한 파일을 사용하지 않는다.

각 오디오 자산은 아래 메타데이터를 가진다.

- 파일 식별자와 원본 파일명
- 녹음 또는 제작 주체
- 녹음 장소·환경(공개 가능한 범위)
- 원본/가공 여부
- 편집·후처리 이력
- 사용 권한과 라이선스 조건
- 게임 내 사용 위치

### 9.2 공간 음향

소리가 화면 좌우 채널에만 고정되지 않도록 3D 위치와 청취자 방향을 기반으로 공간화한다. 거리, 방향, 실내외 구분, 장애물에 따른 음향 변화는 단계적으로 구현한다.

웹에서는 Web Audio API의 AudioListener와 PannerNode를 활용할 수 있다. AudioWorklet은 별도 오디오 처리 로직이 필요한 경우 검토한다. 실제 반사·회절·흡음을 완전하게 계산한다고 주장하지 않고, 성능과 검증 결과에 맞춘 근사 모델임을 기록한다.

### 9.3 접근성 및 안전한 청취

- 큰 소리의 갑작스러운 재생을 제한하는 마스터 리미터
- 전체 음량과 효과음 음량의 개별 조정
- 이명·청각 교란 효과의 강도 조정 또는 비활성화
- 모노 오디오 옵션
- 자막 및 중요 소리의 시각적 보조 표시

## 10. NPC 및 세계 반응

NPC는 단순히 화면에 서 있는 배경 오브젝트가 아니라 세계 상태에 반응하는 캐릭터로 구성한다. 초기 버전은 복잡한 전술 AI보다 안정적인 상태 관리와 자연스러운 애니메이션에 집중한다.

- 주변 사건에 대한 상태 변화
- 이동·대기·대화 등 일반 행동 상태
- 시야와 청각 이벤트를 게임 내부에서 추상적으로 처리
- 장면의 진행 상태와 NPC 상태의 일관성
- 저장 후 다시 불러왔을 때의 상태 유지

실제 전술, 공격 전략, 취약점 공략, 실전 행동 절차를 모델링하거나 학습 자료로 제공하지 않는다.

## 11. 사용자 인터페이스와 조작

### 11.1 UI 원칙

UI는 몰입을 방해하지 않는 최소한의 인터페이스를 기본으로 한다. 그러나 현실감을 이유로 필수 정보나 접근성 설정을 숨기지는 않는다.

### 11.2 조작 설정

- 키보드·마우스 기본 조작
- 키 재설정
- 좌우 눈 감기 키 각각 설정
- 마우스 감도와 시야각 조정
- 그래픽 품질 프리셋
- 오디오 믹서
- 시각·청각 효과 강도 조정
- 자막과 시각적 보조 기능

게임패드 지원은 초기 프로토타입에서 입력 추상화 계층을 만들고, 실제 채택은 미정 항목으로 둔다.

## 12. 웹 기술 아키텍처

### 12.1 권장 후보 스택

| 레이어 | 후보 | 역할 |
|---|---|---|
| 언어 | TypeScript | 게임·UI·상태 로직 |
| 빌드 | Vite 계열 도구 | 개발 서버와 번들링 |
| 3D | Three.js | 장면·카메라·에셋·렌더링 관리 |
| 렌더 백엔드 | WebGPU 우선, WebGL 2 대체 경로 | 호환성에 따른 그래픽 실행 |
| 물리 | Rapier 3D / WASM | 일반 강체·충돌·접촉 시스템 검토 |
| 오디오 | Web Audio API | 공간 음향과 오디오 그래프 |
| 비동기 처리 | Web Workers | 에셋 처리와 일부 계산 분리 |
| 저장 | IndexedDB | 로컬 진행 상태와 설정 저장 |
| 자산 | glTF 기반 3D 자산 등 | 모델·애니메이션 배포 |

이 표는 초기 기술 제안이다. 실제 의존성 버전과 API 선택은 기술 검증 프로토타입 이후 lockfile로 고정한다.

### 12.2 렌더링 전략

Three.js의 WebGPURenderer는 WebGPU를 기본 백엔드로 사용하고, 환경에 따라 WebGL 2 대체 경로를 제공한다. 다만 WebGPURenderer 문서는 일부 기능·커스텀 셰이더의 차이와 마이그레이션 제약을 안내하고 있다. 따라서 처음부터 WebGPU 전용 셰이더에 묶이지 않도록 재질·후처리 계층을 분리하고, WebGPU 및 WebGL 2 경로를 모두 테스트한다. [1]

### 12.3 물리 엔진 전략

Rapier는 웹 플랫폼을 지원하는 물리 엔진이며 JavaScript 패키지가 WebAssembly 모듈로 비동기 초기화된다. 일반 강체 물리 후보로 검토할 수 있다. 그러나 엔진을 도입했다고 현실의 모든 과학 현상이 자동으로 구현되는 것은 아니다. 게임에서 필요한 환경장·재질·오디오 연동 등은 별도 시스템으로 설계하고 검증한다. [2][3]

### 12.4 오디오 전략

Web Audio API는 공간화와 오디오 처리 그래프를 지원한다. PannerNode와 AudioListener를 사용해 3D 위치 기반 청취를 구현할 수 있다. [4]

### 12.5 모듈 분리

권장 런타임 모듈:

- `app-shell`: 로딩, 설정, 세계관 선택, 메뉴
- `world-runtime`: 현재 월드와 장면 상태
- `render-runtime`: WebGPU/WebGL 렌더링
- `physics-runtime`: 일반 물리 세계와 접촉 이벤트
- `environment-runtime`: 날씨·바람·표면·시간
- `player-runtime`: 전신·카메라·시각 입력
- `perception-runtime`: 눈꺼풀·시각 적응·감각 효과
- `audio-runtime`: 녹음 자산·공간화·믹싱
- `equipment-runtime`: 데이터 기반 가상 장비와 상태 관리
- `npc-runtime`: NPC 상태와 행동
- `save-runtime`: 진행 데이터·설정 저장
- `telemetry-dev`: 개발 중 성능·오류 계측(사용자 추적 목적이 아님)

모듈 간 직접 참조를 최소화하고 명확한 이벤트와 상태 인터페이스를 통해 연결한다.

## 13. 웹 배포 및 브라우저 호환성

### 13.1 브라우저 목표

초기 검증은 최신 Chromium 기반 데스크톱 브라우저를 1차 대상으로 한다. WebGPU 지원 여부는 브라우저 버전뿐 아니라 GPU, 드라이버, 운영체제 및 보안 컨텍스트에 영향을 받으므로 실행 시 기능 검사를 수행한다. 2026년 11월 Can I Use의 표에서도 Chromium과 Safari·Firefox 간 지원 차이가 표시되므로 브라우저별 테스트가 필요하다. [5]

### 13.2 대체 경로

- WebGPU가 사용 가능하면 WebGPU 경로를 시도한다.
- 초기화 실패 또는 호환성 문제가 있으면 WebGL 2 경로를 시도한다.
- 두 경로 중 하나라도 사용할 수 없으면 브라우저와 장치 정보를 보여 주고 실행 불가 사유를 설명한다.
- 기능 감지는 User-Agent 문자열만으로 판단하지 않는다.

### 13.3 다운로드와 자산 스트리밍

- 시작에 필요한 최소 자산부터 로드한다.
- 지역·임무별 에셋 패키지를 분리한다.
- 텍스처와 메시의 LOD를 준비한다.
- 오디오 파일은 장면별로 지연 로딩한다.
- 사용하지 않는 자산은 명시적으로 해제한다.
- 진행률, 오류, 재시도 상태를 로딩 UI에 보여 준다.

### 13.4 서버 필요성

싱글플레이 첫 버전은 게임 시뮬레이션과 세이브를 클라이언트에서 처리하는 구조를 기본안으로 한다. 계정, 멀티플레이 서버, 실시간 백엔드는 초기 필수 요소가 아니다. 정적 파일 호스팅과 버전 배포만으로 시작할 수 있는지 먼저 검증한다.

## 14. 성능과 품질 정책

### 14.1 성능 예산

초기 목표 수치는 실제 측정 전의 가설이다. 프로토타입에서 프레임 시간, GPU 시간, CPU 시간, 메모리, 로딩 시간을 측정한 뒤 다시 설정한다.

| 항목 | 초기 목표안 |
|---|---|
| 플레이 프레임률 | 고사양 프리셋 60 FPS 목표, 저사양 프리셋 30 FPS 하한 목표 |
| 프레임 페이싱 | 급격한 프레임 시간 변동 최소화 |
| 메모리 | 장면별 예산 수립, 누수 검사 |
| 로딩 | 최초 실행과 지역 전환을 구분해 측정 |
| 렌더링 | 픽셀 비율·그림자·후처리 품질을 단계화 |
| 시뮬레이션 | 렌더링 품질과 독립된 시간 관리 |

### 14.2 품질 프리셋

- Low: 낮은 해상도 스케일, 제한된 그림자·후처리, 적은 환경 오브젝트
- Medium: 기본적인 PBR, 중간 그림자 품질, 표준 환경 밀도
- High: 높은 해상도 스케일, 고품질 그림자·반사·환경 밀도
- Custom: 사용자가 개별 항목 조절

품질 프리셋은 그래픽 렌더링을 바꾸는 것이며, 핵심 월드 상태·저장 데이터·게임 규칙을 임의로 바꾸지 않는다.

### 14.3 성능 계측

개발 빌드에는 프레임 시간, 렌더링 호출 수, 메모리 사용량, 물리 단계 시간, 오디오 지연, 자산 로딩 시간을 확인할 수 있는 디버그 오버레이를 제공한다. 배포 빌드에서는 개인 식별 가능한 행동 추적을 기본으로 하지 않는다.

## 15. 데이터와 자산 파이프라인

모든 콘텐츠는 별도의 매니페스트를 통해 등록한다.

| 자산 | 관리 데이터 |
|---|---|
| 3D 모델 | 식별자, 파일, LOD, 재질, 애니메이션, 라이선스 |

| 오디오 | 원본, 편집본, 라이선스, 길이, 믹싱 그룹 |
| 환경 프리셋 | 시간·날씨·바람·시각 조건 |

## 16. 저장과 안정성

- 사용자 설정은 로컬 저장을 기본으로 한다.
- 진행 데이터는 버전이 있는 스키마로 저장한다.
- 저장 중 탭 종료나 브라우저 충돌에 대비한다.
- 저장 파일의 스키마 마이그레이션을 테스트한다.
- 손상된 세이브가 전체 설정을 덮어쓰지 않도록 백업 슬롯을 둔다.
- 초기 버전에서 계정 기반 클라우드 동기화를 필수로 만들지 않는다.

## 17. 테스트 및 검증 계획

### 17.1 과학·현실성 검증 원장

각 시뮬레이션 기능은 다음 항목을 기록한다.

1. 적용하려는 현실 현상
2. 참고한 과학·기술 출처
3. 게임 내부 모델
4. 측정하거나 비교할 테스트 조건
5. 허용 오차 또는 품질 기준
6. 계산량을 위해 생략한 요소
7. 게임적 근사 여부와 한계
8. 마지막 검증 날짜 및 담당자

### 17.2 검증 등급

| 등급 | 의미 |
|---|---|
| A — 검증된 원리 | 널리 알려진 원리와 기준 실험에 대해 재현 가능한 검사를 통과 |
| B — 근사 모델 | 과학 원리를 참고하지만 계산량·상호작용 때문에 단순화 |
| C — 연출 모델 | 몰입과 게임 진행을 위한 비현실적 추상화 |
| N — 미구현 | 설계만 존재하거나 아직 동작하지 않음 |

A/B/C/N을 숨기지 않고 개발 문서와 내부 디버그 화면에 표시한다. “완전한 현실”이라는 문구를 쓰려면 해당 기능이 실제로 검증된 범위를 함께 표시해야 한다.

### 17.3 테스트 종류

- 단위 테스트: 개별 상태·계산 모듈
- 통합 테스트: 플레이어·월드·물리·오디오 연결
- 회귀 테스트: 기존 기능이 새 업데이트로 깨지지 않는지 확인
- 브라우저 테스트: 주요 브라우저와 렌더 백엔드 조합
- 성능 테스트: 대표 장면에서 CPU·GPU·메모리 측정
- 접근성 테스트: 강한 시각·청각 효과와 키 재설정
- 저장 테스트: 저장·로드·마이그레이션
- 에셋 검증: 누락 파일·깨진 참조·라이선스 메타데이터

### 17.4 완료 조건

기능의 완료 여부는 “화면에 보인다”가 아니라 다음 조건으로 판정한다.

- 명세가 존재한다.
- 구현이 연결되어 있다.
- 정상 조건 테스트를 통과한다.
- 예외 조건 테스트를 통과한다.
- 성능 비용이 측정되었다.
- 접근성 옵션이 제공된다.
- 자산·라이선스 정보가 확인되었다.
- 알려진 한계가 문서화되었다.

## 18. 개발 단계

### Phase 0 — 기술 검증

목표: 브라우저에서 프로젝트의 핵심 기술이 함께 작동하는지 증명한다.

- Rapier 3D 초기화 및 일반 물체 상호작용

목표: 하나의 테스트 공간에서 1인칭 플레이가 처음부터 끝까지 동작하게 한다.

- 기본 음향 공간화
- 그래픽 설정과 저장

### Phase 2 — 환경 시뮬레이션

목표: 하나의 공간이 정적인 배경이 아니라 변화하는 세계가 되게 한다.

- 시간과 날씨 상태
- 지역별 바람의 게임용 환경장
- 식생·먼지·연기·의복 반응
- 표면 재질 프로필
- 실내외 음향 프리셋

### Phase 3 — 콘텐츠 프레임워크

목표: 세계관과 장비 콘텐츠를 추가할 수 있는 등록 체계를 완성한다.

- REAL WORLD / FICTIONAL WORLD 데이터 구조
- 지역 및 장면 패키지
- 게임 전용 장비 등록과 검증
- NPC 상태 시스템
- 임무/시나리오 데이터

### Phase 4 — 수직 슬라이스 완성

목표: 한 개의 완성된 플레이 구간을 품질 기준에 맞춰 완성한다.

- 완성된 환경과 플레이 흐름
- 실제 녹음 기반 오디오 자산
- 모든 핵심 기능의 테스트
- 성능·접근성·저장 검증

### Phase 5 — 확장 및 베타

- 추가 지역과 시나리오
- 세계관 패키지 확장
- 브라우저 호환성 확대
- 에셋 용량과 로딩 최적화
- 사용자 피드백 기반 개선

## 20. MVP 범위

첫 번째 공개 데모는 대규모 캠페인이나 다수의 세계관 콘텐츠가 아니라, 핵심 기술을 증명하는 작은 테스트 지역으로 제한한다.

### MVP에 포함

- 웹 브라우저 실행
- 싱글플레이 1인칭 이동
- 전신 모델 표시
- 좌우 눈 독립 입력의 기본 버전
- 하나의 테스트 지역
- 포토리얼리즘 방향의 PBR 환경
- 일반 물체의 중력·충돌·표면 상호작용
- 환경 바람에 대한 식생·먼지 등 시각 반응
- 실제 녹음 또는 라이선스 확보된 환경 오디오
- 3D 공간 음향 기본 버전
- 로컬 설정 및 진행 저장
- 디버그 성능 표시

### MVP에서 제외

- 온라인 멀티플레이
- 광범위한 오픈월드
- 다수의 실제 국가·도시 전체 재현
- 완성된 전체 캠페인
- 의학적 수준의 인체 시뮬레이션
- 현실 무기 운용·실측 탄도·폭발물·공격용 무인기 운용 모델
- 웹에서 보장할 수 없는 수준의 완전한 유체·공기역학 계산

## 22. 결정 로그와 다음 작업

### 22.1 바로 다음에 할 일

1. 프로젝트명 없이 저장소와 폴더 구조부터 임시로 구성할 수 있도록 문서·에셋 규칙을 고정한다.
2. 기술 검증용 브라우저 테스트 페이지를 만든다.
3. 렌더러, 물리, 오디오가 함께 작동하는 작은 테스트 장면을 만든다.
4. 전신 1인칭 플레이어의 카메라·몸 모델 연결을 검증한다.
5. 하나의 표면·하나의 환경 바람·하나의 오디오 소스로 시작해 확장성을 확인한다.
6. 첫 수직 슬라이스가 통과한 뒤 콘텐츠 규모와 목표 하드웨어를 결정한다.

### 22.2 우선순위

- P0: 웹 실행, 렌더링 초기화, 물리 루프, 입력, 세이브
- P1: 전신 1인칭, 환경 물리, 공간 음향
- P2: 세계관 데이터 분리, 장비 등록, NPC, 시나리오
- P3: 고급 시각 효과, 대규모 지역, 콘텐츠 확장

## 23. 용어

| 용어 | 의미 |
|---|---|
| PBR | 물리 기반 렌더링. 재질의 빛 반응을 일관된 방식으로 표현하는 렌더링 기법 |
| WebGPU | 브라우저에서 GPU 기능을 활용하는 웹 그래픽·계산 API |

| Vertical Slice | 핵심 품질을 대표하는 작은 구간을 처음부터 끝까지 완성한 검증 버전 |
| Fixed Timestep | 렌더링 프레임과 별도로 일정한 간격으로 시뮬레이션을 갱신하는 방식 |

| Validation Registry | 기능별 근거·테스트·한계를 기록하는 검증 원장 |
